# Звіт до лабораторної роботи №2. NoSQL

**Варіант 13:** Система управління спортивними подіями

## 1. Види NoSQL баз даних

NoSQL — загальна назва баз, які не використовують реляційну модель «таблиці + JOIN» як основну. Зазвичай вони жертвують частиною можливостей SQL (складні JOIN, жорстка схема, іноді сувора узгодженість) заради простішого горизонтального масштабування, гнучкої схеми або швидкості на певному типі запитів.

| Тип | Модель даних | Приклади | Для чого підходить | Слабкі місця |
|---|---|---|---|---|
| Key-value | ключ → значення (рядок, хеш, список) | Redis, Memcached, DynamoDB, RocksDB, DBreeze | кеш, сесії, лічильники, черги, рейтинги | немає запитів за вмістом значення |
| Документна | JSON/BSON-документи з вкладеними об'єктами й масивами | MongoDB, Couchbase, Firestore, LiteDB | дані, які читаються «цілим об'єктом», змінна структура | JOIN між колекціями незручні, дублювання даних |
| Колонкова (wide-column) | рядки з динамічним набором колонок, розподіл за ключем партиції | Cassandra, ScyllaDB, HBase | великі обсяги записів, часові ряди, логи | запити лише за заздалегідь спроєктованими ключами |
| Графова | вузли та ребра з властивостями | Neo4j, ArangoDB | соцмережі, рекомендації, пошук шляхів | погано масштабується горизонтально |
| Time-series | вимірювання з міткою часу | InfluxDB, TimescaleDB | метрики, телеметрія, IoT | вузька спеціалізація |
| Пошукова | інвертований індекс | Elasticsearch, OpenSearch | повнотекстовий пошук, аналітика логів | не основне сховище, слабка транзакційність |

Окремо варто виділити **вбудовані (embedded) NoSQL-бази**: LiteDB (документна), DBreeze, RocksDB, LMDB (key-value). Вони не мають окремого сервера, працюють як бібліотека всередині застосунку і зберігають дані в локальному файлі. Це саме той випадок, коли NoSQL замінює реляційну базу в простих і пет-проєктах: нічого не треба встановлювати й адмініструвати.

## 2. Чи варто виносити частину даних у NoSQL

Основна частина предметної області з лабораторної №1 (турніри, команди, квитки, замовлення, платежі) добре лягає на реляційну модель:

- між сутностями багато зв'язків, і їх треба перевіряти (зовнішні ключі);
- продаж квитків і оплата потребують ACID-транзакцій: одне місце не можна продати двічі;
- потрібні довільні звітні запити з JOIN.

Ці дані **залишаються в SQL Server**.

Але є частина, для якої реляційна модель незручна, — **live-трансляції матчів**. Тут доцільно використати документну базу. Як документну базу обрано **LiteDB**: її API і модель даних (BSON-документи, вкладені масиви, індекси за виразами) аналогічні MongoDB, але вона вбудована. Аргументи за документну модель:

1. **Дані читаються цілим об'єктом.** Сторінка матчу показує все одразу: рахунок, склади, стрічку подій, статистику. У SQL для цього потрібно 5 запитів або JOIN по 7 таблицях, а в документній базі це один документ.
2. **Структура подій різна для різних видів спорту.** У футболі є голи, картки, заміни й кутові, у баскетболі — очки (1/2/3), фоли та тайм-аути з номером чверті. Згодом можуть з'явитися VAR, пенальті, відеоповтори. У SQL це або десятки nullable-колонок, або EAV-таблиця «ключ–значення» (`MatchEventDetails`), яку складно читати й індексувати. У документі кожна подія просто має свій набір полів.
3. **Запис зачіпає один об'єкт.** Подія під час матчу змінює лише документ цього матчу. У SQL вона перетворюється на транзакцію з 3 інструкцій у різних таблицях.
4. **Дані після матчу майже не змінюються.** Тому дублювання (наприклад, ім'я гравця всередині події) не створює проблем з узгодженістю.

Також доцільно додати **key-value сховище** для простих даних, які читаються й змінюються за ключем: кеш live-рахунку, лічильники глядачів, стрічка останніх подій, тимчасове бронювання місця. Для цього обрано вбудовану key-value базу **DBreeze** (розділ 7).

## 3. Нова вимога і модель даних

**Вимога:** система веде live-трансляції матчів. Для кожного матчу зберігаються склади команд, хронологія подій (з різним набором атрибутів для різних видів спорту) і підсумкова статистика. Сторінку матчу відкривають багато вболівальників одночасно, а оператор додає події під час гри.

### 3.1. LiteDB: один документ на матч

```json
{
  "_id": 42,
  "Sport": "Football",
  "TournamentId": 3,
  "TournamentName": "Футбольна ліга 3",
  "Venue": { "Name": "Арена Львів 2", "City": "Львів" },
  "StartTime": "2023-05-14T18:00:00Z",
  "Status": "Finished",
  "Home": {
    "TeamId": 7, "Name": "Буревій Харків 7", "Score": 2,
    "Lineup": [ { "PlayerId": 151, "Name": "Максим Коваленко", "Number": 9, "Position": "FW", "IsStarter": true } ]
  },
  "Away": { "TeamId": 12, "Name": "...", "Score": 1, "Lineup": [ ] },
  "Timeline": [
    { "Seq": 1, "Minute": 12, "Type": "goal", "TeamId": 7, "PlayerId": 151, "PlayerName": "Максим Коваленко",
      "Details": { "bodyPart": "head", "assistId": "160" } },
    { "Seq": 2, "Minute": 25, "Type": "card", "TeamId": 12, "PlayerId": 301, "PlayerName": "...",
      "Details": { "color": "yellow" } }
  ],
  "Stats": { "possession": { "Home": 58, "Away": 42 }, "shots": { "Home": 14, "Away": 9 } }
}
```

Окремо зберігається колекція `teams` з гравцями як довідник. Обидві колекції лежать в одному файлі `data/sportlive.db`.

### 3.2. SQL Server: та сама інформація в 7 таблицях

| Частина документа | Таблиця SQL |
|---|---|
| команди (довідник) | `Teams` |
| гравці (довідник) | `Players` |
| заголовок матчу, рахунок, арена | `Matches` |
| `Home.Lineup`, `Away.Lineup` | `MatchLineups` |
| `Timeline[]` | `MatchEvents` |
| `Timeline[].Details` (змінні атрибути) | `MatchEventDetails` (EAV) |
| `Stats` | `MatchStats` |

Схема — `sql/01_live_schema.sql`, індекси — `sql/02_live_indexes.sql`, еквіваленти всіх запитів — `sql/03_queries.sql`.

### 3.3. Індекси (однакові за змістом в обох базах)

| Призначення | LiteDB | SQL Server |
|---|---|---|
| матчі команди за датою | `$.Home.TeamId`, `$.Away.TeamId` | `IX_Matches_Home_Start`, `IX_Matches_Away_Start` |
| відбір за турніром | `$.TournamentId` | `IX_Matches_Tournament` |
| події за типом | `$.Timeline[*].Type` (по масиву) | `IX_MatchEvents_Type_Player` |
| пошук за містом | **навмисно немає** | **навмисно немає** |

LiteDB не підтримує складені індекси з кількох полів. Тому для пошуку матчів команди виконується два пошуки за індексом (команда вдома і команда в гостях), а результати об'єднуються в застосунку.

## 4. Методика тестування

### 4.1. Середовище

- SQL Server Express встановлений локально як служба Windows. LiteDB 5 і DBreeze працюють усередині тестового застосунку і зберігають дані у файлах на тому ж диску.
- Клієнт — консольний застосунок на C# (.NET 8, Release). Бібліотеки: LiteDB, DBreeze, Microsoft.Data.SqlClient + Dapper.
- Параметри машини (ОС, кількість ядер) записуються в результати автоматично.

### 4.2. Дані

Дані генеруються детерміновано: матч з номером N завжди однаковий (`new Random(N)`). Завдяки цьому **в обидві бази записуються ідентичні дані**, і тест можна повторити з тим самим результатом.

- 200 команд (140 футбольних, 60 баскетбольних), по 25 гравців;
- 30 турнірів, 10 міст, період 2020–2025;
- футбольний матч: 16 гравців у складі кожної команди, 18–31 подія, 8 показників статистики;
- баскетбольний матч: 12 гравців у складі, 25–40 подій з номером чверті, 7 показників.

На 10 000 матчів це приблизно 255 тис. подій, 350 тис. атрибутів подій, 296 тис. записів складів і 73 тис. рядків статистики, тобто близько 1 млн рядків у SQL. На 100 000 матчів — близько 10 млн рядків.

### 4.3. Чому саме такі обсяги

- **1 000** — дані повністю в кеші. Видно «чисту» вартість одного запиту: мережа, драйвер, розбір запиту.
- **10 000** — приблизно 5 сезонів невеликої федерації.
- **100 000** — уже ~10 млн рядків у SQL. На цьому обсязі стає помітною різниця між пошуком за індексом і повним скануванням.
- Більше не беремо, бо SQL Server Express обмежений 10 ГБ на базу, а прогін на 1 млн матчів на ноутбуці займав би години. Тренд між 1k → 10k → 100k уже показує, як операції масштабуються.

### 4.4. Тести та обґрунтування

| № | Операція | Чому саме вона | Що очікуємо |
|---|---|---|---|
| 1 | Картка матчу за id | головний сценарій live-сторінки | LiteDB: 1 документ; SQL: 5 запитів з JOIN |
| 2 | Матчі команди за рік, TOP 20 | типовий список «останні ігри» з фільтром за індексом | обидві бази йдуть за індексом |
| 3 | Топ-10 бомбардирів турніру | аналітика по вкладеному масиву | сильна сторона SQL: GROUP BY по вузькій таблиці подій; LiteDB вибирає з документів лише id авторів голів, а групує застосунок |
| 4 | Підрахунок за полем без індексу | що буде, якщо індекс забули | повне сканування в обох |
| 5 | Додавання голу (live) | основний запис під час матчу | LiteDB: прочитати документ, додати подію, перезаписати документ у транзакції; SQL: транзакція з 3 інструкцій |
| 6 | Оновлення одного показника статистики | точкове оновлення вкладеного поля | обидві бази: одна інструкція за ключем |
| 7 | Пакетна вставка 1000 матчів | імпорт архіву | `InsertBulk` проти `SqlBulkCopy` у 5 таблиць в одній транзакції |
| 8 | Паралельне читання карток, 8 потоків, 5 с | поведінка під навантаженням, коли сторінку відкриває багато людей | пропускна здатність, оп/с |
| — | Початкове завантаження і створення індексів | вартість наповнення бази | LiteDB пише документи цілком, SQL Server розкладає ті самі дані на 5 таблиць з індексами |

### 4.5. Як вимірюється

- Перед кожним тестом є **прогрів** (5–10 % ітерацій), він не враховується: перші запити підіймають пул з'єднань, кеш планів і кеш сторінок.
- Кожна операція виконується **багато разів** (від 10 для повного сканування до 1000 для читання за id) з різними випадковими параметрами. Для обох баз параметри однакові.
- Рахуються **медіана і 95-й перцентиль**, а не лише середнє. Середнє сильно псують поодинокі паузи (збирання сміття, фонові процеси), а медіана показує типовий час. p95 показує, наскільки стабільна база.
- Час вимірюється на клієнті від виклику до отримання **готового C#-об'єкта**. У SQL до цього входить і збирання об'єкта з 5 наборів рядків, бо застосунку потрібен саме об'єкт, а не рядки.
- **Перевірка коректності:** перед тестами програма порівнює відповіді обох баз (картки матчів, агрегації, фільтри). Якщо вони відрізняються, це видно в результатах. Порівнювати швидкість різних відповідей немає сенсу.
- Для SQL використовується штатний спосіб роботи: параметризовані запити, пул з'єднань, `SqlBulkCopy` для масової вставки. Для LiteDB — типізовані LINQ-запити з проекцією (вибираються лише потрібні поля) та вирази BsonExpression.

### 4.6. Що свідомо не тестується

- **Холодний старт** (порожній кеш після перезапуску): він залежить переважно від диска, а не від моделі даних, і його складно відтворити однаково.
- **Кластер і шардинг:** вимагають кількох машин, а вбудовані бази їх не підтримують у принципі.
- **Паралельний запис:** LiteDB допускає лише одного записувача одночасно (блокування файлу), тому паралельний тест виконується лише для читання. У live-сценарії події одного матчу додає один оператор.

### 4.7. Обмеження порівняння

- Обидві бази працюють одночасно і ділять оперативну пам'ять. Тести виконуються по черзі, а не паралельно.
- **Вбудована база проти клієнт-серверної.** LiteDB працює в тому ж процесі, тож кожен запит обходиться без мережевого виклику. SQL Server — окремий процес, і кожен запит проходить через мережевий стек, навіть локально. Це не недолік методики, а саме та різниця, яку отримує невеликий проєкт, коли замінює сервер БД вбудованою NoSQL. Але при порівнянні дрібних операцій це треба враховувати.
- LiteDB пише зміни в окремий журнальний файл і періодично переносить їх в основний (checkpoint), тому розмір файлу бази під час роботи змінюється.

## 6. Аналіз результатів і висновки

### 6.1. Де виграє документна база

**Картка матчу.** LiteDB у 10–38 разів швидша на всіх обсягах, а час майже не залежить від кількості матчів. Це очікувано: документ читається одним зверненням за первинним ключем. SQL Server стабільно витрачає близько 3 мс, бо виконує 5 запитів із JOIN, передає 5 наборів рядків і збирає з них об'єкт. Під паралельним навантаженням різниця ще помітніша: 15–32 тис. операцій за секунду проти 1,4–1,8 тис.

**Запис під час матчу.** Додавання голу і зміна статистики в LiteDB у 1,5–4,7 раза швидші. Хоча LiteDB перезаписує документ повністю, це одна операція з одним об'єктом. У SQL додавання голу — це транзакція з трьох інструкцій у трьох таблицях. На 1 000 матчів результат однаковий, бо там обидві бази впираються в постійні накладні витрати на транзакцію.

**Масове завантаження.** Документи вставляються у 2–3,8 раза швидше, ніж ті самі дані, розкладені на 5 таблиць через `SqlBulkCopy`. На 100 000 матчів SQL Server записував близько 10 млн рядків, а LiteDB — 100 тис. документів.

Усе це сценарії «працюємо з одним матчем цілком», тобто саме ті, заради яких live-дані виносилися в документну базу. Отже, вибір моделі даних для цієї частини системи себе виправдав.

### 6.2. Де виграє реляційна база

**Пошук матчів команди.** На 1 000 матчів LiteDB ще швидша, але вже на 10 000 SQL Server випереджає її вдвічі, а на 100 000 — у 14 разів. Причина в індексах. У SQL є складений індекс `(HomeTeamId, StartTime DESC)`: сервер одразу переходить до потрібної команди й потрібних дат і бере перші 20 рядків. LiteDB не підтримує складених індексів, тому за індексом знаходить усі матчі команди (на 100 000 це ~1 000 документів), читає їх, а дату фільтрує й сортує вже в пам'яті.

**Агрегація по вкладеному масиву.** Топ бомбардирів на малих обсягах швидший у LiteDB, а на 100 000 SQL Server виграє в 2,4 раза. Щоб порахувати голи, LiteDB мусить прочитати кожен документ турніру (~3 300 документів по кілька кілобайт), хоча потрібен лише id автора голу. SQL Server читає лише вузький індекс по таблиці подій.

**Повне сканування.** Без індексу SQL Server швидший на всіх обсягах, а на 100 000 — у 16 разів. Документ матчу містить склади, 20–40 подій і статистику, тому для перевірки одного поля `City` LiteDB розбирає весь документ. SQL Server сканує лише таблицю `Matches`, де рядок займає близько сотні байтів.

Отже, **денормалізація — це не безкоштовна оптимізація**. Вона пришвидшує читання об'єкта цілком, але сповільнює все, що проходить по багатьох об'єктах і потребує лише кількох полів. З ростом обсягу цей ефект посилюється: на 1 000 матчів LiteDB виграє майже скрізь, а на 100 000 SQL Server випереджає її у 2–16 разів на всіх запитах по колекції.

### 6.3. Застереження щодо порівняння

Частина переваги LiteDB на дрібних операціях пояснюється тим, що вона вбудована і не витрачає часу на мережевий виклик до окремого процесу. Для невеликого проєкту це реальна перевага вбудованої бази. Але для системи з кількома серверами застосунку вбудована база не підходить, бо до файлу може писати лише один процес. На великих операціях, тобто агрегаціях і скануваннях, мережеві витрати непомітні, і там результат визначає саме модель даних та індекси.

На 1 000 матчів картка в LiteDB читалася повільніше, ніж на 10 000 (0,30 проти 0,08 мс). Найімовірніше, це ефект прогріву: на малому обсязі вимірювання займає лічені мілісекунди, і на нього сильніше впливають JIT-компіляція та кеш. Тому основні висновки зроблено за обсягами 10 000 і 100 000.

### 6.4. Висновки

1. Live-дані матчу (склади, стрічка подій, статистика) доцільно зберігати в документній базі. Сторінка матчу читається в 10–38 разів швидше, а запис подій — у 2–5 разів швидше, ніж із 7 таблиць SQL. Крім того, події різних видів спорту зберігаються без EAV-таблиці.
2. Пошук за довільними полями, звіти й агрегації по всіх матчах залишаються сильною стороною SQL Server, особливо на великих обсягах. Їх варто виконувати в реляційній базі або рахувати заздалегідь. Наприклад, таблицю бомбардирів можна оновлювати в key-value сховищі при кожному голі (розділ 7, пункт 5), а не рахувати агрегацією.
3. Оптимальна архітектура — гібридна: SQL Server для квитків, оплат і звітності, документна база для live-трансляцій, key-value сховище для кешу, лічильників і бронювань.
4. Key-value база DBreeze записала 100 000 ключів за 138 мс і виконала 10 000 випадкових читань за 112 мс. Для доступу за ключем це дуже швидко, але будь-який запит, крім пошуку за ключем чи діапазоном ключів, доводиться закладати в дизайн ключів заздалегідь.

## 7. Друга NoSQL: DBreeze (key-value)

DBreeze — вбудована key-value база для .NET. Вона зберігає пари «ключ → значення» у впорядкованому дереві на диску, підтримує ACID-транзакції та обхід ключів у прямому й зворотному порядку. На відміну від документної бази, вона нічого не знає про вміст значення: шукати можна лише за ключем або діапазоном ключів. Тому вся логіка запитів закладається в **дизайн ключів**.

Код — `src/SportLive.Benchmark/KeyValueDemo.cs`, вивід — `results/keyvalue_output.txt`.

| № | Операція | Як реалізовано | Застосування |
|---|---|---|---|
| 1 | Запис і читання за ключем | `Insert`, `Select`, перевірка `Exists` | кеш live-рахунку `match:42:score` |
| 2 | Лічильник | читання + запис в одній транзакції з `SynchronizeTables` | глядачі трансляції |
| 3 | Об'єкт як значення | JSON-рядок у значенні, оновлення поля | кеш картки матчу |
| 4 | Діапазонні запити | ключ `матч:хвилина:номер`, `SelectForwardStartsWith`, `SelectBackwardStartsWith`, `SelectForwardFromTo` | стрічка подій, останні 3 події, події першого тайму |
| 5 | Рейтинг | ключ `t1|(999 − голи)|гравець`, ключі вже відсортовані | таблиця бомбардирів |
| 6 | Множини | ключі-пари `team:1|user:2`, обхід за префіксом | підписники на сповіщення |
| 7 | Запис з часом життя | значення `користувач|час закінчення`, перевірка в транзакції | бронювання місця на 10 хвилин |
| 8 | Транзакції | `Commit` і транзакція без `Commit` | гол = рахунок + стрічка атомарно |
| 9 | Агрегати за ключами | `Count`, `Min`, `Max` | кількість подій |
| 10 | Видалення | `RemoveKey` | зняття бронювання |
| 11 | Масові операції | 100 000 записів однією транзакцією, 10 000 випадкових читань | оцінка швидкодії key-value доступу |

Пункти 5 і 7 добре показують природу key-value бази. Тут немає ні сортування за значенням, ні вбудованого часу життя ключа, як у Redis. Тому рейтинг будується через ключ, у якому кількість голів записана так, щоб звичайний порядок ключів давав спадання. А час закінчення бронювання зберігається в самому значенні й перевіряється в транзакції.

Бронювання місця вирішує проблему, якої немає в схемі з лабораторної №1: поки покупець оплачує, місце має бути заблоковане, але не назавжди. Транзакція в key-value базі атомарно перевіряє, чи місце вільне або бронювання прострочене, і лише тоді займає його.

## 8. Базові запити LiteDB

Файл `src/SportLive.Benchmark/LiteDbQueriesDemo.cs` демонструє:

- `Insert`, `FindById`, `Delete`;
- зміну документа під час матчу (гол) і `Update`;
- додавання події нового типу (VAR) з іншим набором полів без зміни схеми;
- `UpdateMany` з виразом, тобто оновлення без читання документа;
- фільтр за елементами вкладеного масиву: `$.Timeline[@.Type = 'goal' AND @.Minute <= 5]`;
- LINQ-запит із сортуванням, проекцією і лімітом;
- SQL-подібне групування `GROUP BY` з `COUNT` і `AVG`;
- `EXPLAIN`, щоб показати пошук за індексом (`INDEX SEEK`);
- перегляд індексів колекції через системну колекцію `$indexes`.

Вивід цих запитів записується в `results/litedb_queries_output.txt`.
